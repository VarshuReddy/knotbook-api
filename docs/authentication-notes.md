# KnotBook Backend: Authentication Notes

## 1. Authentication vs Authorization

**Authentication:** Verifies who the user is.

Example: Checking whether the email and password are correct.

**Authorization:** Determines what the authenticated user is allowed to access.

Example: Ensuring User A cannot access User B's crochet projects.

Authentication happens first, followed by authorization.

## 2. PasswordEncoder and BCrypt

Passwords must never be stored as plain text.

During registration:

```java
String encodedPassword =
        passwordEncoder.encode(request.getPassword());
```

BCrypt generates a salted password hash.

During login:

```java
passwordEncoder.matches(
        request.getPassword(),
        user.getPasswordHash()
);
```

`matches()` checks whether the entered password corresponds to the stored hash.

We do not decrypt BCrypt hashes.

**Why BCrypt?**
- One-way password hashing.
- Automatically handles salts.
- Computationally expensive to make brute-force attacks harder.

## 3. JWT Authentication

JWT stands for JSON Web Token.

It allows the backend to authenticate requests using a signed token.

A JWT consists of three parts:

```text
Header.Payload.Signature
```

### Header
Contains token metadata, such as the signing algorithm.

### Payload
Contains claims about the authenticated user.

Our access token contains:

- Issuer
- Subject (user ID)
- Email
- Issued-at time
- Expiration time

### Signature
Verifies that the token was generated by a trusted signer and hasn't been modified.

Important: JWT payloads are encoded, not encrypted. Never store passwords or sensitive personal information in JWT claims.

## 4. JwtEncoder vs JwtDecoder

### JwtEncoder

Used when generating a JWT.

In KnotBook, it:
1. Receives JWT claims.
2. Uses the configured HS256 algorithm.
3. Signs the token using our secret key.
4. Returns the signed JWT string.

Used during login and token refresh.

### JwtDecoder

Used when validating an incoming JWT.

It:
1. Reads the bearer token.
2. Verifies its signature.
3. Checks expiration.
4. Validates the issuer.
5. Returns the validated JWT.

Spring Security uses the decoder through the OAuth2 Resource Server JWT support.

Important: We use JWT bearer-token infrastructure, not Google OAuth login.

## 5. Access Token vs Refresh Token

### Access Token

- Signed JWT.
- Short-lived.
- Validates API requests.
- Expiration: 15 minutes.
- Validated by Spring Security.

### Refresh Token

- Cryptographically random opaque string.
- Longer-lived.
- Used to obtain new access tokens.
- Expiration: 30 days initially.
- Stored as a hash in MySQL.
- Can be revoked and rotated.

### Why use two tokens?

A short-lived access token limits the time a stolen access token can be used.

The refresh token allows the user to remain logged in without entering their password every 15 minutes.

## 6. Refresh Token Lifecycle

```text
LOGIN
  |
  v
Generate access token
  |
Generate refresh token
  |
Hash refresh token
  |
Save hash in MySQL
  |
Return both tokens
  |
  v
ACCESS TOKEN EXPIRES
  |
  v
Android sends refresh token
  |
  v
Backend hashes supplied token
  |
Find matching database record
  |
Validate expiry and revocation
  |
Revoke old refresh token
  |
Generate new access token
  |
Generate new refresh token
  |
Store new refresh-token hash
  |
Return both new tokens
```

The old refresh token must never be reusable after successful rotation.

## 7. Why hash refresh tokens?

We store only the SHA-256 hash of the refresh token in MySQL.

The original token is returned to Android.

During refresh:
- Android sends the original token.
- Backend hashes it.
- Backend looks up the hash in MySQL.
- If valid, the token is rotated.

If the database is compromised, the attacker cannot directly use the stored hashes as refresh credentials.

## 8. Stateless Authentication

Our SecurityConfig uses:

```java
SessionCreationPolicy.STATELESS
```

This means Spring Security does not maintain an HTTP session to remember authenticated users.

Every protected request must contain:

```http
Authorization: Bearer <access_token>
```

Spring Security validates the token for each request.

The refresh-token database is separate from the HTTP session mechanism.

## 9. Spring Security Configuration

### SecurityFilterChain

Defines:
- Public endpoints.
- Protected endpoints.
- Authentication mechanism.
- Session management.
- CSRF configuration.

Our public authentication endpoints:

```text
/api/auth/register
/api/auth/login
/api/auth/refresh
/api/auth/logout
```

Other endpoints require authentication.

### PasswordEncoder

Spring-managed bean responsible for password hashing and matching.

### JwtEncoder

Spring-managed bean responsible for signing access tokens.

### JwtDecoder

Spring-managed bean responsible for validating access tokens.

## 10. Spring Boot Architecture

### Controller

Handles HTTP requests and responses.

Example: AuthController.

### Service

Contains business logic.

Example: AuthService.

### Repository

Communicates with the database using Spring Data JPA.

Example: UserRepository.

### Entity

Represents a database table.

Examples: User and RefreshToken.

### DTO

Defines API request and response structures.

DTOs prevent exposing database entities directly to clients.

## 11. Transactions

`@Transactional` manages a database operation within a transaction.

A transaction ensures that related database changes succeed or roll back together.

Example: During token refresh, revoking the old token and creating its replacement should happen in one transaction.

JPA dirty checking detects changes to managed entities and synchronizes them with the database when the transaction commits.

## 12. Flyway vs Hibernate

### Flyway

Manages database schema versions through SQL migration files.

Examples:

```text
V1__create_app_users_table.sql
V2__create_refresh_tokens_table.sql
V3__create_projects_table.sql
```

Flyway tracks executed migrations in `flyway_schema_history`.

### Hibernate

Maps Java entities to database tables and manages persistence.

Our configuration:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

Hibernate validates entity mappings against the database schema.

Flyway creates and changes the schema. Hibernate validates and works with it.

## 13. API Status Codes

| Status | Meaning |
|---|---|
| 200 | Successful request |
| 201 | Resource created |
| 204 | Successful request with no response body |
| 400 | Invalid request |
| 401 | Authentication failed or token invalid |
| 403 | Authenticated user lacks permission |
| 404 | Resource not found |
| 409 | Duplicate or conflicting resource |

## 14. Important Security Rules

- Never store plain-text passwords.
- Never expose password hashes in API responses.
- Never commit JWT secrets to Git.
- Never store raw refresh tokens in MySQL.
- Always validate access tokens.
- Rotate refresh tokens.
- Revoke refresh tokens on logout.
- Never trust client-supplied user IDs for authorization.
- Protect against concurrent refresh-token reuse.
- Use HTTPS in production.
